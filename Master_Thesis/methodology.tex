\subsection{Dataset}
Our benchmark uses the NYC taxi dataset\footnote{\url{https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page}}, which is publicly available. We use specifically the trip data of yellow taxi cabs during 2025, totaling 1.2 GB split across 12 files (one for each month). This dataset provides a good representation of real-world stream data, since taxi trips are constantly occurring. Further, the dataset can be easily extended to include data from previous years, in case there is the need to scale up the benchmark.

As a preprocessing step, we added a single column to the dataset with an integer id for each trip. This helps us collect statistics for each trip processed by our system and it also increases reproducibility of our results.

\subsection{Data ingestion}
Following the approach of previous works, we ingest the dataset into a Kafka broker instance, using the Kafka Python client API\footnote{\url{https://docs.confluent.io/platform/current/clients/confluent-kafka-python/html/index.html}}. Producing the data happens in a separate Python process, so that our benchmark can consume those events independently. For reproducibility purposes, the broker runs in a Docker container.

\subsection{Data format}
We use the Arrow format for data representation in our benchmark. Apache Arrow\footnote{\url{https://arrow.apache.org/}} is a standardized, in-memory columnar format, which facilitates data exchange between systems that implement the format. The columnar layout of Arrow data also makes it very efficient for writing it in Parquet format \cite{ApacheArrowFrequently}. Furthermore, the Arrow specification includes an inter-process communication (IPC) mechanism, which can be used to stream arrow data while avoiding the use of serialization or extra copies to/from the in-memory Arrow layout. Therefore, we use the IPC mechanism for producing data to the Kafka broker, so that the consumer can read it as Arrow data directly.

\subsection{Lakehouses}
Our benchmark can interact with the different lakehouse systems in two ways. The default way uses a dedicated library\footnote{\href{https://py.iceberg.apache.org/}{PyIceberg}, \href{https://delta-io.github.io/delta-rs/}{delta-rs} and \href{https://duckdb.org/}{DuckDB}} for each system, which is optimized for that specific lakehouse format and is compatible with Arrow data. Alternatively, the benchmark can be run with DuckDB as the client for all three lakehouse formats, since it has first-class support for all three formats \cite{DuckDBDocumentationLakehouse2025}. In both cases, the client used to interact with the lakehouse is considered part of SUT and is reported explicitly for clarity of results.

Additionally, all catalog servers are run on Docker containers, so that the benchmark can be run on any machine, thus contributing to reproducibility of experiments. The only exception is when using DuckDB as a catalog for DuckLake. In that case, the catalog is stored in a local file. This combination is only used when running experiments that involve the "data inlining" feature (Section \ref{sec:ducklake-inlining}).
